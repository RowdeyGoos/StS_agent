## Objective and coverage accounting

Support the pinned build's events through reusable interaction handlers and
small explicit event connections. "All events" is the program objective, not
current evidence. Establish a finite event inventory and record each event's
branches and interaction families with separate implemented, fixture-tested and
live-demonstrated states. An unclassified event or branch is an open gap; the
existence of a shared selector class does not establish its caller's rules.
Natural encounter discovery and strategic option selection are separate from
successfully controlling a user-prepared event.

The predecessor generic event controller handles bounded ordinary choices, one
item child and final Proceed. The predecessor card parent handles only Cheese and Smith.
Its shared pure card core supports add/remove/transform/upgrade with explicit
counts, but this does not enable those operations on arbitrary game events.

The [68-type coverage matrix](research/PHASE_1_EVENT_COVERAGE_MATRIX.md) now records
the metadata inventory and per-type branch gaps. The corrected census established
the type denominator without member bodies or runtime eligibility claims.

## First integrated increment — functional gate passed

The implementation described below is reviewed and its 40-file source identity
is frozen. Candidate and frozen aggregate gates passed, with 244 reported checks
across 12 suites and four matching native builds across the two gates. Repository
regression passed 1,243 tests. The [acceptance ledger](research/PHASE_1_EVENT_ORCHESTRATOR_V1_ACCEPTANCE.md)
records exact evidence. Release composition and live validation remain separate.

Create `event_orchestrator_v1` beside the frozen components. Unify ordinary event
choices, the existing exact item-reward handler and the proven Cheese add-two
card handler beneath one event parent. Add explicit child kind, child ordinal
and accepted-parent-action lineage. Allow a bounded sequence of children with
only one active at a time. The event parent retains sole authority to choose
options and Proceed; the existing card parent must not independently repeat
those actions. Reuse the actual frozen item and card selection implementations.

The Python host gains an immutable observation-to-legal-action decision-provider
seam. Use an explicitly selected deterministic first-legal provider for control tests;
provider output must be validated before one reserved action. This is not a
learned or strategic event policy. Unknown transitions stop with an explicit
unsupported result; no screen adoption after an uncertain action or fallback
clicking is allowed.

A functional gate must cover actual C# core-to-Python composition and compiled
native connections, not only a synthetic standalone router. A later installable
release requires its own complete composition, reproducibility, verifier,
package, operational and live gates. Functional acceptance alone is never
reported as live readiness.

## Coverage expansion

In parallel, inspect only bounded pinned-build event metadata and explicitly
selected method bodies after recording the finite selection. Use the established
metadata/IL inspector without executing target assemblies. First determine event
classes and interaction families; then select concrete caller evidence for card
remove/transform/upgrade/add variants, optional or multiple selections, rewards,
embedded combat and custom event screens. Event names and localized prompts do
not establish numeric rules or exact effects.

Add callers by interaction family, retaining exact option/controller and effect
bindings. A coverage row can advance only when its required branches, counts,
confirmation modes, complete candidate domain and completion witness are known.
Repeated-choice loops, multiple reward episodes, scrolling, custom screens and
combat handoff remain explicit gaps until their own semantics and tests pass.
Do not hide these gaps behind an "ordinary event" classification.

## Preserved boundaries

Keep public structured observations separate from encoded learning observations.
Keep one owner-frame mutation at a time, recapture before dispatch, reserve
before mutation, exact action/result correlation, bounded total work and no retry
on uncertainty. Parent options remain unavailable while a child is active.
Child completion and exact effect are prerequisites for parent continuation;
ordinary option-screen transitions are not independently verified HP/gold effects.
Every event exit requires explicit Proceed and the bound map handoff.

No profile/save filesystem, Steam Cloud changes, retained live corpus, remote
Git or unrelated capability expansion. The user's event-development request
selects event capability expansion only. Existing frozen contracts/packages and
user changes are preserved; newer contracts supersede scope only in new siblings.
No live game setup is needed during this repository phase.
