# Item V1 isolated direct-collection contract

- Date: 2026-09-05. Frozen for isolated implementation after independent acceptance.
- Baseline: `951620a`, selected 23cf integration checkout. Static scope is `PHASE_1_MISSING_ROOM_API_SCOPE.md`.
- Purpose: implement the smallest native-bound item collection component needed by the observed event follow-up. This is an unselected successor, not an extension of live 0.8.0 or its host protocol.

## Evidence and boundary

The pinned reward button's ordinary click starts asynchronous synchronized selection. Return from click is dispatch only. The retained reward's `SuccessfullySelected` is set after its `OnSelect` and `AfterRewardTaken` await. Exact `ClaimedRelic`/`ClaimedPotion` getters are pure field reads. A full potion belt can mark the reward taken with no acquisition, so potion completion also requires an exact inventory transition. Reward screens may auto-close; reconcile retained model facts before classifying the foreground UI.

Implement only direct collection of visible potion/relic offers on a topmost visible `NRewardsScreen`. Reject a mixed gold/card/unknown reward screen, unpopulated offers, invalid/duplicate indices, mismatched player, invalid item keys, excess bounds, already-selected reward, map-open input, or ambiguous UI. No shop purchase, item skip/decline/replacement, parent event progression, Proceed, route, bootstrap, installation or live enablement. Relic hooks and synchronization internals remain stopped dependencies. Exact retained claimed-model plus selected flag proves this narrow reward-local relic acquisition; do not infer relic-count change, hook fidelity or parent completion.

## Frozen component semantics

1. Each component instance permits one reserved dispatch total and one bound run/player/reward-screen. No reset or second-surface API. The future live composition must own exactly one instance for its bounded invocation. Before dispatch, a missing screen may wait, but a different run/player/screen after binding permanently fails closed. This screen-identity rule applies only before dispatch; after reservation, foreground screen changes are ignored while retained run/player/reward facts reconcile. No native reference/address/ID is emitted. Use a caller-provided fresh 32-lowercase-hex session nonce and fixed surface ordinal `1` for correlation, never for game information.
2. Ready observation contains version `item_v1`, session nonce, surface ordinal, a canonical SHA-256 decision ID, up to eight offers ordered by unique native RewardsSetIndex (bounded to 0..255), item kind and bounded stable model ID, enabled state, and legal `collect:<index>` candidates, where index always means the native RewardsSetIndex in invariant decimal (no leading zero except 0), including receipts and resolved results. There is no separately renumbered public slot. Copy up to eight potion slots in UI order, preserving null slots and total capacity. Keys are conservatively restricted to 1..128 ASCII letters/digits/underscore; any other target key is unsupported. No arbitrary text fields. Disabled offers have no action. Potion offers have no action when no slot is empty. A mixed relic/potion screen may advertise only its enabled relics in that case. A potion-only full/zero-capacity belt is unsupported; when every otherwise eligible control is disabled, return waiting with no decision. Never publish ready with zero candidates. Zero visible offers is waiting; any visible unsupported offer makes the screen unsupported. No current active parent/event identifier is fabricated.
3. The decision digest includes version, session/surface, every ordered visible offer's index/kind/key/enabled status, exact ordered potion keys including empties/capacity and legal candidates, using unambiguous invariant encoding, specified in a checked-in canonical encoder and sensitivity fixtures before integration. Ready records and all baselines own immutable copies. Internal bindings additionally retain exact run/player/screen/button/reward/offered-model references; those references never enter public hashes or output.
4. Apply accepts only an exact currently published decision ID and advertised action. Immediately recapture the same top visible screen and all public facts, and compare all internal bindings (including the offered objects and ordered inventory object references), current button visibility/enabled state, and public digest. Invalid/stale/unsupported requests perform zero dispatch. A potion requires at least one empty slot at this immediate revalidation.
5. Atomically install pending retained reward/player/offered model and copied before-inventory, reserve this decision/action and increment the one-dispatch budget BEFORE native dispatch. Ordinary `NRewardButton.ForceClick()` is the only native mutation. Never invoke Reward.OnSelect, commands, synchronizer methods, inventory mutation, screen removal or parent controls. Reentrant apply/read during dispatch cannot publish another action or resolve early. Return an exact accepted dispatch receipt only if dispatch returns normally. A throw yields a fixed uncertain outcome, permanently disables action, retains reservation/budget and cannot be retried; exception detail is not emitted.
6. After accepted dispatch, no other legal action can be published. Reconciliation reads retained run/player/reward/offered model facts before UI classification, without dereferencing a freed reward button or removed screen. Same run/player is required; missing or changed context fails closed. A child or closed overlay alone proves nothing and does not erase pending facts. Polling is bounded to 256 reads after dispatch; read number 256 may resolve, otherwise it expires to a fixed unsupported result and retains budget. The limit is an offline component bound, not a claim about elapsed live time.
7. Relic resolves only when the exact retained reward has SuccessfullySelected=true and its ClaimedRelic is reference-equal to the offered model with the same stable key. Potion additionally requires unchanged capacity/order and exactly one formerly null slot now containing the exact offered model/key; every other slot (including empty slots) must retain reference identity and key. No replacement, same-key different object, unrelated change, multiple insertions, capacity drift or full-belt false claim can resolve. While selected=false, unchanged inventory or the exact anticipated insertion may wait for async completion; any other delta fails closed. Claimed mismatch once nonnull fails closed. Selected=true with null claim is terminal failure; for potion, selected=true without the exact sole insertion is also terminal failure. Read/validation exceptions fail closed with fixed output only. Every post-reservation failure (including changed context, inconsistent claim/delta, exception or poll exhaustion) latches permanently: later reads return the same failure without target reads, actions or later resolution.
8. Resolved result is stable across repeated reads and includes only version, session nonce, surface ordinal, original decision ID, original action ID, offer index, kind, key and result `collected`. This is item-local reconciliation, not parent completion. No current decision or legal actions accompany it. Public output must not include native references, retained model internals, exception strings or unrelated game values. A rejected or uncertain apply never produces this resolved record.
